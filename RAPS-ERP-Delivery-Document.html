2. Ownership and Control

The system runs on Amazon Web Services. The AWS account is registered in the company’s name under admin@rameshs.ind.in, with the company’s own billing details and payment instrument. The consequences are the most important statements in this note:

  • The company, not the developer, is the account holder. AWS invoices the company directly. The developer is not in the payment path and cannot alter the bill. No charge can be raised without the company’s own payment instrument, and removing it stops the service.
  • The database, all documents and all backups sit inside that account, on servers physically in India. No component stores data outside India.
  • There is no hosting fee, licence fee, per-user fee or subscription payable to the developer. The entire cost of running the system is the AWS invoice in Section 4.
  • If the relationship with the developer ended today, the system would keep running and the company would retain complete control of it.

The site is served over an encrypted connection. Passwords are stored scrambled and cannot be read by anyone, including the developer. The database is not reachable from the internet, and the backup storage is private and rejects all public access.

6. Backups

A backup runs automatically every Sunday at 00:30 India Standard Time. Nobody has to remember it and nobody can forget it. Each run takes a complete copy of the database and of every uploaded document, seals them into one file with a manifest, and uploads it to separate private storage in the Hyderabad region.

If the company wants that exposure reduced, the backup can be run daily instead. It is a scheduling change only and adds roughly $0.10 to $0.20 per month.

8. How Changes Are Made From Here

This is one central system running one version for everybody. Nothing is ever downloaded, installed or updated by a user. A change is made once, in one place, and everyone has it.

The sequence

  1. Requested in writing, stating the screen, what it does today and what it should do instead. This fixes the scope and avoids disagreement later about what was asked for.
  2. Written and tested on a separate copy. The live system staff are using is never edited directly and never used as a testing ground.
  3. Recorded in the version control history with date and description, giving a permanent dated record of what changed and when.
  4. Deployed to the live server, and received by users at their next page refresh. No action required from anyone.

Work that may interrupt use is notified at least 24 hours ahead to admin@rameshs.ind.in and scheduled outside working hours, ordinarily Sunday between 22:00 and 06:00 IST.

Protections that apply to every change

Data is never overwritten by an update. An update replaces programme code. It does not replace, reset or clear business records: purchase orders, work orders, stock, documents and the audit log all survive. Structural changes are applied as numbered ordered revisions, 107 to date, and the system refuses to start against a database that has not received them in the correct order, so a half-applied change can never go live. The Sunday backup is scheduled independently of any deployment, so a copy from before every change always exists. Any change can be reversed from the version control history.
